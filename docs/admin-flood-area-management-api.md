# Admin Flood Area Management API



## Jira Task



CCF-113 - ADMIN-BE-02 Implement Flood Area Management API



## Purpose



Provide APIs for active Admin accounts to create, list, view, update and delete flood areas.



These APIs use the existing `flood\_areas` collection.



The public endpoint `GET /api/flood-areas` remains available.

## Authentication and Authorization



All Admin flood area endpoints require:



Authorization: Bearer <token>



POST and PATCH requests with JSON also require:



Content-Type: application/json



The authenticated account must:



\- Exist in the users collection.

\- Have isActive set to true.

\- Have role set to admin.



The backend checks the current account in Firestore in addition to JWT authentication and role middleware.



Do not send an actor ID, actor role or audit data in the request body.



## Endpoint Summary



| Method | Path | Purpose | Success |

| --- | --- | --- | --- |

| GET | /api/admin/flood-areas | List flood areas | 200 |

| GET | /api/admin/flood-areas/:areaId | Read one flood area | 200 |

| POST | /api/admin/flood-areas | Create a flood area | 201 |

| PATCH | /api/admin/flood-areas/:areaId | Update selected fields | 200 |

| DELETE | /api/admin/flood-areas/:areaId | Delete an unreferenced flood area | 200 |



Replace :areaId with a real flood area document ID.



## Flood Area Fields



| Field | Type | Rules |

| --- | --- | --- |

| id | string | Generated by the backend |

| name | string | Required, trimmed and non-empty |

| description | string or null | Optional; omitted or blank values become null |

| geometry | object | Required polygon geometry |

| severity | string | low, medium, high or critical |

| status | string | active or inactive |

| source | string | Required, trimmed and non-empty |

| createdAt | string or null | Backend timestamp serialized as ISO 8601 UTC |

| updatedAt | string or null | Backend timestamp serialized as ISO 8601 UTC |



The client cannot set id, createdAt or updatedAt.



Only these fields are accepted in create and update bodies:



\- name

\- description

\- geometry

\- severity

\- status

\- source



Unsupported fields return HTTP 400.



## Polygon Geometry



Example:



{

&#x20; "type": "polygon",

&#x20; "points": \[

&#x20;   { "latitude": 16.0544, "longitude": 108.2022 },

&#x20;   { "latitude": 16.0560, "longitude": 108.2060 },

&#x20;   { "latitude": 16.0520, "longitude": 108.2080 }

&#x20; ]

}



Rules:



\- type must be exactly "polygon".

\- points must be an array containing at least three points.

\- Each point must contain numeric latitude and longitude.

\- Coordinates must be finite numbers.

\- Latitude must be between -90 and 90.

\- Longitude must be between -180 and 180.

\- Unsupported geometry and point fields are rejected.



This API does not currently validate polygon topology, including self-intersections, collinear points or duplicate vertices.



Use geometry.points for polygon coordinates. A separate location field is not supported by this API.

## 4. Update a Flood Area



PATCH /api/admin/flood-areas/:areaId



Send only the fields to change.



Example:



{

&#x20; "severity": "medium",

&#x20; "source": "Updated manual admin entry"

}



Example to deactivate an area:



{

&#x20; "status": "inactive"

}



Success:



HTTP 200



{

&#x20; "success": true,

&#x20; "message": "Flood area updated successfully",

&#x20; "data": {

&#x20;   "floodArea": {

&#x20;     "...": "The updated flood area fields"

&#x20;   }

&#x20; }

}



Rules:



\- The body must contain at least one supported field.

\- Omitted fields keep their existing values.

\- Supplied fields must pass validation.

\- If geometry is supplied, send the complete geometry object.

\- The original createdAt is preserved.

\- Additional stored fields are preserved.

\- updatedAt changes when stored values change.

\- Sending values identical to the stored values returns 200 without updating timestamps or creating another audit event.

\- Updating a missing area returns 404.



The Admin account check, area read and update are performed in one transaction.



## 5. Delete a Flood Area



DELETE /api/admin/flood-areas/:areaId



Send no body or an empty JSON object:



{}



Success:



HTTP 200



{

&#x20; "success": true,

&#x20; "message": "Flood area deleted successfully",

&#x20; "data": {

&#x20;   "id": "example-area-id"

&#x20; }

}



Deletion rules:



\- The area must exist.

\- No flood\_alerts document may reference the area through areaId.

\- Both active and inactive alerts prevent deletion.

\- Deletion permanently removes the area document.

\- Audit records are retained.

\- Reading the deleted area returns 404.

\- Deleting a missing area returns 404.

\- Non-empty or invalid delete bodies return 400.



If an alert references the area:



HTTP 409



{

&#x20; "success": false,

&#x20; "message": "Flood area is referenced by flood alerts; set status to inactive instead"

}



The UI should offer changing the area status to inactive when deletion is blocked.



Do not automatically delete related flood alerts.



The Admin account check, area read, reference query and deletion are performed in one transaction.



## Flood Alert Reference Protection



createFloodAlert and setFloodAlertById now check the referenced flood area inside their write transactions.



This coordinates with the Admin deletion transaction to protect against orphaned references when an alert is written while an area is being deleted.



Both alert write helpers reject a missing referenced area.



Mock tests cover competing alert creation and area deletion. Real Firestore concurrency verification is still pending.



## Audit Logging



Successful changes use the shared best-effort audit logging service.



| Operation | Audit action | Target type |

| --- | --- | --- |

| Create | flood\_area.create | flood\_area |

| Update | flood\_area.update | flood\_area |

| Delete | flood\_area.delete | flood\_area |



Audit fields:



\- actor.id: authenticated Admin ID.

\- actor.role: admin.

\- target.id: affected flood area ID.

\- timestamp: backend server timestamp.

\- metadata.source: api.

\- metadata.outcome: success.

\- metadata.changedFields: changed field names only.



Create records the six supported area fields.



Update records only fields whose normalized values changed.



Delete records an empty changedFields array.



Read operations, rejected requests and updates without changes do not create audit events through these endpoints.



Audit events do not store old or new field values.



Audit logging runs after the business transaction commits. Audit write failure does not roll back a successful area operation.



This is best-effort logging; audit storage and the area change are not one atomic transaction.



## Public API Compatibility



GET /api/flood-areas remains available without authentication.



Its existing response fields remain:



\- id

\- name

\- description

\- geometry

\- severity

\- status

\- source



Admin responses additionally expose createdAt and updatedAt.



Do not assume that the public endpoint filters out inactive areas; the existing implementation returns all stored areas.



## Error Responses



Error format:



{

&#x20; "success": false,

&#x20; "message": "Error description"

}



| HTTP | Meaning |

| --- | --- |

| 400 | Invalid body, field value or document ID |

| 401 | Missing/invalid authentication or authenticated account no longer exists |

| 403 | Account inactive or current role is not admin |

| 404 | Flood area does not exist |

| 409 | Flood area is referenced by flood alerts |

| 500 | Unexpected server or database error |



Document IDs must be non-empty strings after trimming. They cannot contain a slash, be "." or "..", or exceed 1500 UTF-8 bytes.



## Frontend Integration



Use the existing login flow and token storage.



For list screens:



1\. Call GET /api/admin/flood-areas.

2\. Read data.floodAreas.

3\. Handle loading, empty and error states.



For create forms:



1\. Collect the supported fields.

2\. Send coordinates as numbers.

3\. Call POST /api/admin/flood-areas.

4\. Show success only after receiving HTTP 201.

5\. Refresh the list or open the returned area ID.



For edit forms:



1\. Load the area detail.

2\. Send selected changes through PATCH.

3\. Replace displayed data with data.floodArea from the response.



For delete actions:



1\. Ask the user to confirm deletion in the UI.

2\. Send DELETE.

3\. Remove the row after a successful response.

4\. If the response is 409, display the message and offer deactivation.



Hide Admin management actions for non-admin accounts. The backend independently enforces access.



Convert ISO 8601 UTC timestamps to local time for display.



Do not automatically retry create requests after a timeout: the first request may already have been saved.
